## Phase 2A — Shared design foundation — ✅ implemented, awaiting approval

**Result (26 Nov 2026):** homepage tokens promoted to `fp.css`; one 1440px outer container (`.fp-container` = `.wrap`); approved masthead and footer generated by `apply-shell.js` on all 95 pages with active state by content type; masthead behaviour moved to `fp.js`; header/footer breakpoints unified; tools page in the global shell; 176 dead CSS rules and the dead carousel/menu JS removed after reference checks; internal files blocked in `.htaccess`. Homepage pixel-identical at 8 viewports; SEO and `<main>` fingerprints identical on all 94 public pages; 50/50 functional checks; 188 page loads clean. Details: `docs/PHASE-2A-REPORT.md`.

**Depends on:** Phase 1 (approved build) — built on the local approved build because Phase 1 was not yet pushed.

**Scope**
- Promote the homepage width system (`.fp-container`, `--content-max-width`, `--page-gutter`) and homepage-only tokens (`--ember-strong`, `--ember-label`, card surface/border literals) into shared tokens in `fp.css`.
- Make the approved masthead and footer the site-wide header and footer, generated by `apply-shell.js` for every page (one header, one footer), keeping each page's active state.
- Move masthead, dropdown and drawer behaviour from `fp-home.js` into `fp.js` (or a small shared module); retire the old menu code.
- Unify breakpoints with the homepage set.
- Remove dead CSS/JS from the previous homepage (`fp.css` §10, §19; old hero carousel in `fp.js`) after confirming nothing else uses it.
- Give `/tools.html` the shared shell.
- Stop `.md` files and `/docs/` from being publicly served (`.htaccess`).

**Deliverables:** updated `fp.css`, `fp.js`, `apply-shell.js` (and `fp-home.css` slimmed to homepage-only sections); component list updated in `DESIGN-SYSTEM.md`; before/after screenshots of the homepage and one page of each type.

**Acceptance criteria**
- Homepage pixel-identical (or explained ≤1px differences) to `docs/design-references/` at all 8 viewports.
- Every page has the same masthead and footer; correct active nav item; dropdowns, drawer, search work everywhere.
- Content never wider than 1440px; no overflow anywhere; no console errors; all scripts idempotent.
- No article `<main>` content, URL, canonical or metadata changed.

## Phase 2B — Editorial listing pages

**Depends on:** 2A.
**Scope:** News, Reviews, Compare (editorial comparisons), Buying Guides, Car Culture listings restyled in the homepage language: compact page head, filter tabs, card grid using homepage card patterns, clean-image rules (fallback tile when only a text-baked graphic exists), pagination/"Load more" if lists outgrow one page.
**Deliverables:** updated listing markup generation in `build-lists.js`, CSS, screenshots.
**Acceptance:** existing filters and hash links (e.g. `/reviews.html#suv`) still work; no URL changes; same QA bar as 2A.

## Phase 2C — Article detail templates

**Depends on:** 2B.
**Scope:** One article design covering news, buyer's briefs/reviews, editorial comparisons, guides, explainers and car-culture stories, applied through CSS and generator changes (not by rewriting article bodies). Byline, label, hero with credit, quick verdict, score breakdown, buyer-fit, FAQ, Sources, Read Next; responsive hero images (srcset) without touching article text.
**Acceptance:** every article's `<main>` text content unchanged (byte-compare text nodes); structured data unchanged; Lighthouse mobile performance and accessibility not lower than today.

---

## Phase 3 — Vehicle intelligence

**Depends on:** 2A (shell); can overlap 2C.
**Scope:** Cars directory, brand pages, model pages, variant information, upcoming and recently launched cars — all fed from a centralized, verified data file (extend `data/cars.json`: brand, model, generation, variants, powertrains, prices with source + date, safety, media, related articles). Model pages link every article about the model and vice versa.
**Deliverables:** data schema, generator script for vehicle pages, first set of model pages for cars FlamingPiston already covers, upcoming-cars page with confirmed vs expected dates.
**Acceptance:** every figure has a source and check date; no invented data; new URLs approved before creation; sitemap updated; no duplicate content with existing briefs.

## Phase 4 — Interactive buying intelligence

**Depends on:** 3 (needs the data).
**Scope:** advanced filters on the Cars directory (the homepage finder lands there), spec comparison and variant comparison from the data, per-model ownership calculators (reusing `fp-tools.js` logic), further tools (petrol vs EV, depreciation only when reliable data exists).
**Acceptance:** results are computed from sourced data only; assumptions shown; works without a backend; keyboard and screen-reader usable.

## Phase 5 — Supporting pages

**Depends on:** 2A.
**Scope:** search results page (from `search-index.json`), About, Contact, Author, editorial standards, legal pages, 404 — restyled in the shared language.
**Acceptance:** legal and policy text unchanged unless Gagan edits it; search overlay and results page agree.

## Phase 6 — Administration and backend

**Depends on:** 3–4 proving that manual JSON editing is too slow or error-prone.
**Scope:** centralized vehicle management, price updates, source verification, publishing workflow, media management. Supabase (or similar) only if justified on cost and maintenance for a solo founder.
**Acceptance:** written justification approved first; static site keeps working if the backend is down; no paid service without approval.

## Phase 7 — Website-wide QA and deployment

**Runs:** before every release, fully before any major launch.
**Checklist:** responsive screenshots at 8 viewports; accessibility (contrast, focus, keyboard, labels, reduced motion); performance (image weight, LCP, CLS); SEO (titles, descriptions, canonicals, structured data, sitemap, RSS, robots); broken links and missing images; data accuracy (prices and dates in `data/*.json`, pre-launch articles); publishing scripts run cleanly and idempotently; Gagan's approval before push.
